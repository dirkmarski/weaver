# Durable lessons (iterations 1-20)

Only lessons still valid, compressed by theme (pruned at the it17-it20 closes per governance/memory-architecture.md). "it" = iteration, "#" = issue. Evidence is in `work-log/`.

## Scoping and spec
- Ask the PM before guessing: open behavioural questions go to the PM before development or acceptance (it2; #36). Raising them mid-issue also works when found late: in it12 three PM decisions (Q1-Q3) were recorded in the issue's Change log, so reviewer, tester and acceptance had one source.
- Scope from observed user pain and personas, not only the candidate list (it6, it8); do a data spike before a hard feature (it8 pointing; it12 ring noise on 10 seeds; it13: denser Tricky generation was too slow, p90 865 ms with failures, so Hint preference was chosen instead).
- Settle wording and visuals with persona mock-ups plus a short play check before writing the issue; mock-up choices can flip in play (it9-it11). Side-by-sides on the same replayed positions settle it fast: #56 in two rounds (it12); #65 with screenshots of real positions incl. the worst case and a notes-filled variant plus a contrast calculation (it14). Re-check readability on the real page at acceptance: #65 notes in hatched cells scored 4/5 on the mock-up, 3/5 on the page. A blind A/B pair must differ only in the variable under test (it15: the key text also differed and a persona noticed).
- A key line must name every mark it relies on; personas flagged a missing "hatched = ..." entry (it14).
- Pin concrete examples, and check each pin against the exact state named (it10 #46, it11 #50). Criteria written mid-issue name a commit, not "today" or "main" (it12 #56 AC3 said "as main" where main had a different layout). The same holds for examples the lead puts in prompts: ask the agent to verify them (it16 #72: the lead's four-cell example shared a box; the developer caught it). A seed pin ("seed N after k hints") names its walk (unit walk = `hintFor` without level; page walk = real Hint clicks on the level) and is re-run in that walk before the issue is written: #96's "seed 38 after 13 hints" came from a spike walk and did not reproduce on the page (it20).
- Check a visual criterion for feasibility with measurements before it goes into the issue, on the worst-case content. In #56 the PM's Q2 criteria were contradictory (the developer measured and stopped, it12). In #61 the feasibility figure used one glyph; the chip width follows the digit, so D = 1 was 1.94 px against a 2 px minimum (it13). It works when done up front: in it18 the PM measured every numeric AC of #83-#85 in two injected-CSS spikes on the real page, and all three issues were accepted without a spec rejection.
- Criteria judging the same outcome must agree: #85 AC6 asked a persona average >= 4 at 360x740 while AC2 promised only a partial fit for seed 1 there; the PM accepted with deviation D9 (average 3.67, seed 8 4.33). Cross-check score targets against the fit the other ACs promise.
- When a wording fix changes grammar, check every variant (a/an, singular/plural, each form): "this D" fixed "a 8" but read oddly with two rings (it12); #61 pinned one example per form and ring count (it13).
- Teach before rewarding, but close an uncounted-technique gap quickly (it8 #36 -> it9 #42); a hint alone does not make a technique practisable, a level built for it does (it8 #37).
- Deliver issues in sequence and fold wording nits into the next issue touching the same section (it6-it8).
- Perceived layout: empty reserved space reads as broken (the blank reserve, it18-it20: a reserve needs content or a cue), and content flush with the viewport edge reads as clipped (#97: the scrolled invitation ended 0.9 px above the fold; two personas called it cut off). Leave a visible margin, and set persona score targets the spike beats with margin (#97 met its 4.0 key target exactly).

## Testing
- Follow the test strategy: golden path, edge cases, error conditions; small independent oracles on a few seeds; no sweeps (#35 cut 15 s of sweeps to 0.6 s with a rule -> test mapping).
- Page wiring is tested in the repo now (`tests/page.test.js`, #55). New UI behaviour adds targeted page scenarios there; page evidence must show skipped = 0. Things only a page test catches: precedence decided in UI wiring (#51 M13), clearing paths, CSS placement, and values a wrapper passes to a pure helper (in #56 the key helper called with a constant or the wrong count survived until a zero-ring page assertion was added). A page test that builds its expected value with the helper it exercises checks wiring only; pin literal text on the page (#61, #65 f1b). Seeded page cases must actually reach each branch: #65's f2 seed always gave a hidden single, so the naked-single gate was unguarded until a naked case was added; #68's issue pins were all hidden-form, so the pointing-digit choice (naked form: digit != pointDigit) survived until f1d was pinned. Check the spec's pins against every branch of a choice, not only the ACs.
- Assert the contract, not only a tolerance: a 1 px "inside the cell" check let the removal of the right-edge rule pass (-0.59 px); pinning the flush edge killed it (#56 R1). Measure exact edges; `clientWidth` is integer-rounded. A loose layout bound guards little: #85's one grid-top assertion (<= 88 px) let the `#status` margin, caption and `#level` mutants survive, so the 360x740 seed 8 fit (3.5 px slack) rests on acceptance measurement only; pin the critical fit itself when slack is thin.
- Click/tap UI needs real input: the suite uses `element.click()`/`focus()`, so testers and the PM drive CDP `Input.dispatchMouseEvent`/`dispatchTouchEvent`/`dispatchKeyEvent`, where the focusout -> click order is real (it16 #72: 5160-step random walk, 0 mismatches). A page test should still fire the click that follows a focus (it killed reviewer M2).
- Visual checks need narrow widths (375 px), numeric rects (`getComputedStyle(td, '::after')` vs note glyph Ranges) and a screenshot look (#56 D1). When a size depends on content (glyph width, text length), measure and guard every variant or the proven worst case: in #61 developer, reviewer, tester and lead all measured one digit and only PM acceptance caught D = 1; f4 now asserts the minimum over digits 1-9. A test message that claims "narrowest" must be proven (it13).
- Ordered precedences need one test per adjacent pair, and shared expressions a test per branch (#45, #46). Seeded tests guard a rule only if a seed fails under the mutant (#37).
- Layout figures must cover the worst element and the real width: measure the last element of a wrapped row (it17 #76: the lead quoted the Hint row bottom, New puzzle on the wrapped second row was clipped at 375x812, caught by the tester), and know the mode: `setDeviceMetricsOverride` with `mobile: false` keeps a 15 px classic scrollbar (375 px gives 360 px content), `mobile: true` gives phone overlay scrollbars. Width-derived sizes (`100vw`) include a classic scrollbar, so phone-layout tests use `mobile: true` (#83). A vertically centred page that no longer fills the viewport moves when content appears; #83 top-aligned below 560 px.
- A new styled control needs a computed-style pin against its sibling (font, padding) and each early-return branch of a handler its own focus assertion: in #90 four CSS mutants and the Hint-branch focus survived a thorough behaviour suite (reviewer). `element.click()` in page tests does not move focus: move it away before asserting.
- New overlay marks need a check against existing cell content (it10 badge over note 3, fixed in #56).
- Use a negative control (run a regression test on the pre-fix commit) for fixes (it2).
- Harness code (#55): clean up on signals too (`node --test` exits on SIGINT/SIGTERM without waiting for its child, which then dies on EPIPE unless stdout/stderr error listeners catch it; remove a temp profile only after the child exits); repeat signal trials at varied delays (the lead's 6 trials found the race review missed); a wait-for-ready loop throws at its bound instead of giving up silently.

## Review
- Re-run claimed survivors and claimed coverage yourself; reports can be wrong both ways (it9 #42; it12 the developer's "right-edge mutant killed" described a different edit). Check each mutant's `git diff` is non-empty before scoring it: macOS `sed -i ''` can silently match nothing, and a no-op mutant reads as "survived" (it19).
- A new predicate needs a mutant per branch: in #60 the naked branch of `isSingle` survived the whole suite while being reachable; one pinned state (seed 26 after two entries) killed it (it13).
- When tests are removed to stay in the ratio budget, list each with the test that still covers it and have the reviewer and tester confirm by mutant (#61, #65). The lead also checks each removal against the ACs: in #65 round 1 a removal dropped the unit cases AC 8 explicitly required, and all other gates had agreed it was redundant. A removal can also unguard a neighbouring condition: in #84 dropping a 10th-row case left the outer `grid.length !== 9` check unguarded (lead mutant; restored in one line). Packing lines to fit the cap is not acceptable (development practices: legible formatting); unpack and pay with listed removals. Check new test lines against the file's longest line: in #90 a 542-character assertion (main max 320) packed five declarations to fit the cap; the lead rejected it and a 214-character set compare kept the key mutants, leaving two CSS mutants to measurement.
- Check an "equivalent mutant" claim against reachable states, not hand-built inputs, and then remove the dead code rather than keep it unguarded (#65 de-dup in `addReasons`; #68 `q !== p` in `ringLink` and the focusout `relatedTarget` check, both dead or observably redundant).
- Targeted mutation spot checks (about 6-15) on risky logic, wiring and CSS find real gaps; before asking for a test of "cleared on path X", check that X is reachable with that state (#56: two equivalent/unreachable mutants). On layout issues the lead asks the reviewer for scroll and style mutants: in #97 three survived a passing suite (the Hint-handler scroll path reached only when a hidden single needs a scroll, the selected link style, the no-scroll guard); a tests-only rework killed them.
- Review by following data from creation to use; check which visual states can co-occur and style only reachable ones (it1, #51).
- Prefer extracting shared logic over duplicating a rule (#42); give even "nit" refactors the full gates (it5).
- Check README claims sentence by sentence against behaviour (it2 onwards).

## Coordination
- Supervise by fixed-format evidence reports, then targeted lead spot checks (Dirk's lead.md supervisor strategy, it15): diff stat vs the claimed file list, `git diff | grep '^-'` in tests vs the claimed removals, a suite run, one re-run mutant, the AC map vs the issue, a screenshot look. Agents list what they did not test; that list drives the rework. Testers leave a usage README in their scratch folder; in it18 the PM and lead re-ran the tester's scripts from it without asking. A print-only probe is not a check: the inherited "Enter on focused button" line printed false on main for two issues unnoticed (fixed at the it18 close to assert). Ratio/count lines in the developer's issue-log section go stale after rework and can be wrong (#91: page +32 claimed, +21/-12 actual); check `git diff --stat`, the lead section is authoritative (#84). For a behaviour-neutral rework round the lead re-runs the tester's saved scripts instead of a tester re-run (it15: 134 checks + replay vs main), and checks that a re-run script actually wrote fresh output (start time vs output timestamps). Keep the tester worktree until that re-run is done: scripts default to it (ROOT ../wt-test), and in #96 the lead removed it first and read stale output that looked like a pass (caught by the timestamp; held in #97).
- Reviewer/tester setup: process.md step 4 (one at a time, log commit in a detached worktree, lead `merge --ff-only`; it19 #91 had no agent merge commits). Replaces agents pushing and merging with `--no-edit` (it4-it18; #90 tester merge ed54240 was untagged). Remove agent worktrees after each issue merge (it17 left three and an orphan commit).
- Re-check levels (rule in process.md "Rework re-checks") came from it8-it12 and it16 #72; the lead can run a tests-only delta re-check itself (it18 #83 rework 1: three mutants re-run, all killed).
- The lead's own delta re-check pays: in it12 it found the #55 signal race after review and test had passed.
- Restart from `memory/wip/current.md` and the wiki; do not read the work log unless needed (Dirk, 1464355); update WIP at every hand-off. Facts needed at scoping (layout figures, persona scores) belong in the wiki, not only in a product log (it18: the PM read the 178-line it17 product log for layout figures; now in product.md).
- Verify every hand-off on GitHub (PR head, acceptance comment) and merge with the accepted sha (it6-it12).
- Personas at scoping and acceptance; forbid helper scripts, solvers, source, README and LOG.md in their prompts (it6). Show them real screenshots without naming the cell: the text-only it16 round missed what the on-screen round found. Check each persona claim against the screenshot and score locating errors (a misplaced ring) apart from the criterion: in #91 3/3 rightly flagged the step-2 naming gap while two misread ring positions (it19). Brief with literal paths (process.md conventions).
- Run every agent whose report the next step needs in the foreground: the lead's reviewer, tester and PM, and the PM's personas. Backgrounded agents let the caller hand back before reports arrived (it16 #72 acceptance incomplete; it17 two #78 lead runs lost review and test). Parallel background runs save little next to a lost run.
- Keep each log file on one branch line (rule in process.md conventions; zero log conflicts in it18-it19, replacing the it17 `iteration-N` branch that caused an add/add conflict). Logs/memory commits go on the issue branch after the accepted code head, and the merge uses that head. An uncommitted PM log on main's tree goes onto the first issue branch (it19).
- Session-id tagging and the LOG.md rule are in process.md conventions; they slip unless written into each prompt (it14: two merges used git's default message).

## Tooling
- `gh pr edit` fails (token lacks read:org): use `gh api -X PATCH repos/dirkmarski/weaver/pulls/N -F body=@file` (issues: `.../issues/N`); merge with `gh api -X PUT .../pulls/N/merge -f merge_method=merge -f sha=<accepted head>`. Retry if GitHub is still computing mergeability (it2, it9).
- Never `git pull --rebase` on a branch that merged main; use `--no-rebase` (it9). Agents sharing a worktree `git add` their own files only (it9).
- Never `rm -rf` a variable that may be unset or default (use `${VAR:?}`); create private temp dirs with explicit paths under the session scratchpad (it13 incident: a failed chain left TMPDIR at the system default; the sandbox refused the delete). run-task gives each session TMPDIR=/tmp/wvr/tmp-<id8> (removed on exit since ac56a00) and the scratchpad lives under /tmp/wvr/claude-502/...; macOS mktemp still ignores TMPDIR. Keep the rule in every agent prompt that uses temp dirs.
- On Node 24 run `node --test` without a path. macOS has no `timeout`; BSD `sed -i ''` cannot match `\n` (use `perl -0pi` or Python for multi-line edits). README lines are very long: spot-check README diffs with `--stat` or `--word-diff`.
- Headless Chrome: `--headless=new --no-sandbox`, temp `--user-data-dir`, `--remote-debugging-port=0` and read `DevToolsActivePort`; kill the process group. Its window has a ~500 px minimum: use `Emulation.setDeviceMetricsOverride` for phone widths and wait for layout (a 25 px cell was once read mid-layout). Focus events (`focusin`/`focusout`) fire only after `Emulation.setFocusEmulationEnabled({enabled: true})` (it15). `Input.dispatchKeyEvent` Enter activates a focused button only with `text: '\r'` on the keyDown (it18 close).
- Scratch scripts can reuse `launch` from `tests/chrome.js`; compare against main with `git archive origin/main` into a scratch dir. Check leftover processes/profiles with a private `TMPDIR` when agents run in parallel.
- CDP touch: `Emulation.setTouchEmulationEnabled({enabled: true, maxTouchPoints: 5})` for touch viewports and `{enabled: false}` for mouse runs (it19 tester/PM libs).
